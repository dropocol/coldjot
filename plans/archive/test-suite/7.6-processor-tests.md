# 7.6 — Processor tests

> **Goal:** verify the glue between BullMQ and the domain — each `*Processor` deserializes a `Job` and calls the right domain service. Thin tests; the logic lives in the services (covered by 7.2).
>
> **Depends on:** [7.1](./7.1-repository-fakes.md) + [7.2](./7.2-unit-domain-services.md). **Feeds:** 7.7.

## What to write

For each `*Processor` under `apps/mailops/src/services/jobs/`, construct it with fake repos + a fake `JobManager`. Feed a BullMQ `Job` constructed without a real worker:

```ts
const job = { id: "job-1", data: emailJobData } as unknown as Job;
await processor.process(job);
expect(fakeJobManager.addEmailJob).toHaveBeenCalledWith(...);
```

### Processors to cover

| Processor | File | What the test asserts |
|---|---|---|
| `EmailProcessor` | `services/jobs/email/processor.ts` | Job → `SendEmailService.send` called with the right `SendEmailOptions`; on success the tracking is marked sent. |
| `ScheduleProcessor` | `services/jobs/schedule/processor.ts` | Job → due contacts polled → `JobManager.addEmailJob` called per due contact. |
| `ContactProcessor` | `services/jobs/contact/processor.ts` | Job → contact sync path. |
| `ListSyncProcessor` | `services/jobs/list/processor.ts` | Job → list sync (paginated contact fetch, sync-record status updates). |
| `SequenceProcessor` | `services/jobs/sequence/processor.ts` | Job → sequence step dispatch. |

Also cover `BaseProcessor.onFailed` (DLQ copy path) now that it takes the DLQ map via constructor (Phase 6.2) — seed a non-empty DLQ map, fail a job, assert the DLQ `add` fired.
