# 7.2 — Unit tests for domain services

> **Goal:** fast unit tests for each `*ServiceImpl` in `services/domain/`. Pure logic — no DB, no BullMQ, no real Gmail.
>
> **Depends on:** [7.1](./7.1-repository-fakes.md) (the fakes). **Feeds:** 7.7.

## What to write

For each of `TrackingServiceImpl`, `SendEmailServiceImpl`, `InboxSyncServiceImpl`, `LaunchSequenceServiceImpl`, `RunScheduleServiceImpl`:

- Construct the service with fake repos + a fake adapter (e.g. `FakeMailTransport` that records sends and returns canned ids).
- Test each public method's happy path + edge cases (below).
- These tests are **fast** (<100ms each) because no DB, no BullMQ, no real Gmail.

### Per-service coverage

**`TrackingServiceImpl` (`services/domain/tracking.service.ts`)**
- `handleEmailOpen` — first open (creates OPENED event + updates stats), repeat open (increments openCount, no new event), unknown hash (no-op).
- `handleLinkClick` — happy path (click record + CLICKED event + stats, returns original URL), unknown link hash (throws "Invalid tracking data").
- `createTracking` — happy path; missing required metadata fields throws.
- `trackEmailEvent` — happy path; unknown tracking id throws.

> **Note:** `handleLinkClick`'s writes still go through a `prisma.$transaction` (the residual flagged in the refactor's STATUS.md). The unit test mocks `@coldjot/database`'s `prisma.$transaction` to run the callback against fakes — same pattern Phase 0's Group B uses. Collapsing the tx client onto the repo is out of scope here (would be a behavior-touching follow-up); pin current behavior.

**`SendEmailServiceImpl` (`services/domain/send-email.service.ts`)**
- `send` happy path — transport.send → delay → getSentDetails → insert untracked → delete original → markTrackingSent + recordSentEvent.
- `disableSending` shortcut — fake IDs, no transport calls, tracking + event still written.
- transport throws 401 → re-thrown as `TOKEN_EXPIRED`.
- transport throws SMTP 535/AUTH XOAUTH2 → re-thrown as `TOKEN_EXPIRED`.

**`InboxSyncServiceImpl` (`services/domain/inbox-sync.service.ts`)**
- `handleNotification` — reply (REPLIED event + contact update + stats), bounce (BOUNCED), original message (no event), already-processed (skip), large history gap (HISTORY_GAP record, watch historyId updated), missing watch/mailbox/token (early return).

**`LaunchSequenceServiceImpl` — ⚠️ IMPL DOESN'T EXIST YET**

`services/domain/launch-sequence.service.ts` is **interface-only** today. Before writing these tests, implement `LaunchSequenceServiceImpl` (launch / pause / resume / reset). The current logic lives in `controllers/sequence.controller.ts` + `services/jobs/sequence/helper.ts` — move it behind the interface, constructor-injecting repos + `JobManager` + `MonitoringService` (mirror the Phase 6 factory pattern). Then:
- `launch` — sequence not found (404), no steps (400), no contacts (400), happy path (enqueues job + starts monitoring).
- `pause` / `resume` / `reset` — status transitions; reset clears rate limits + status → draft.

**`RunScheduleServiceImpl` — ⚠️ IMPL DOESN'T EXIST YET**

`services/domain/run-schedule.service.ts` is **interface-only** today. Implement `RunScheduleServiceImpl.tick()` before testing — the current logic lives in `services/jobs/schedule/processor.ts`'s `processScheduledEmails`. Then:
- `tick` — N due contacts → N email jobs enqueued with correct business-hours-aware delays.
