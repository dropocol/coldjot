## Context — why this exists

Phase 6 left `launch-sequence.service.ts` and `run-schedule.service.ts` as interfaces only. The composition root wired them to `notYetWired` placeholders that threw on call:

```ts
const notYetWired = (name: string): never => {
  throw new Error(`composition-root: ${name} is not wired yet. …`);
};
```

The live logic lived in `controllers/sequence.controller.ts` (launch/pause/resume/reset) and `services/jobs/schedule/processor.ts` (`processScheduledEmails` + `processEmail`). This step moves that logic behind the service interfaces — the last bit of production code the refactor tracked as "Phase 7 scope".

## What was done

### 7.2a — `LaunchSequenceServiceImpl` (`services/domain/launch-sequence.service.ts`) — `74c8bdc`
- Added `LaunchSequenceServiceImpl` next to the existing interface (co-located, matching `tracking.service.ts` / `send-email.service.ts` — Phase 4b.5 decision).
- **Typed domain errors:** `SequenceNotFoundError`, `SequenceHasNoStepsError`, `SequenceHasNoContactsError` (exported from the same file).
- `launch` / `pause` / `resume` / `reset` bodies lifted from the controller. All deps constructor-injected (sequence repo, business-hours repo, JobManager, MonitoringService, rate-limit service).
- **Controller thinned to a HTTP adapter** — `createSequenceController` now takes a single `LaunchSequenceService` dep; the four handlers catch the typed errors and map them to `notFound()` / `badRequest()`, preserving the exact HTTP contract (404 "Sequence not found", 400 "Sequence has no steps", etc.).

### 7.2b — `RunScheduleServiceImpl` (`services/domain/run-schedule.service.ts`) + wiring — `eee9eed`
- Added `RunScheduleServiceImpl` next to the interface. `tick()` owns the full schedule loop: find due → per contact: rate-limit gate → resolve step (deleted-step no-op via `handleMissingStep`) → `calculateNextRun` → build `EmailJob` → `jobManager.addEmailJob` → mark SCHEDULED → increment counters. Per-contact try/catch with the bounded-retry policy (`SCHEDULE_MAX_FAILURES` / `SCHEDULE_FAILURE_BACKOFF_MS`).
- `rateLimitService` + `scheduleGenerator` default to their module exports so module-level `vi.mock` applies when the service is constructed with no overrides (the Group D test relies on this); the composition root passes the real instances.
- **`ScheduleProcessor` thinned** — `process()` delegates to `service.tick()`. Keeps the constructor (BullMQ topology setup) + dev helpers (`checkNextScheduledEmail`, `advanceToNextEmail`). Holds a `RunScheduleService` with a default impl so `new ScheduleProcessor(q, jm)` still works.
- **Composition root** — `launchSequence` + `runSchedule` slots wired to the real impls; the `notYetWired` placeholder helper is deleted entirely.

## Design decisions (recorded for the permanent suite in 7.2)

- **Error model: domain throws, controller maps.** The launch-sequence service is HTTP-agnostic — it throws typed errors; the controller catches + maps to HTTP statuses. The 7.2 unit tests assert against the thrown error classes, not HTTP codes.
- **Schedule tick: service owns the full loop.** Matches the refactor's stated end-state (services own domain logic; processors are thin BullMQ glue). The alternative — service owns only the pure core, processor keeps the retry loop — would have left the processor thick.
- **`resetSequence` + `updateSequenceContactStatus` stay as function imports** from `services/jobs/sequence/helper.ts` (still shared with the email/sequence processors; not worth duplicating or re-injecting yet).
