# 7.5 — Repository tests against a real test DB

> **Goal:** test every `Prisma*Repository` against a real test database. These are the only tests that catch Prisma-specific bugs (typos in field names, missing `include`, wrong relation shape).
>
> **Depends on:** nothing in this plan (needs infra — see Setup). **Feeds:** 7.7 (integration uses the same DB).

## Setup (one-time)

- A dedicated test database (separate from dev). Connection string in `DATABASE_URL_TEST`.
- Add a `postgres_test` service to `docker-compose.yml` (or reuse `postgres` with a separate DB).
- A `beforeEach` that **truncates all tables** (or wraps each test in a transaction that rolls back) — don't rely on test ordering.
- A helper `packages/database/src/test-db.ts` exporting a `prisma` client pointed at the test DB + a `resetDb()`.

These are the slowest tests — run them only in CI (or locally with `docker compose up test-db`).

## What to write

For each `Prisma*Repository` under `apps/mailops/src/repositories/prisma/`, test that each method writes/reads correctly. Example:

- `PrismaEmailTrackingRepository.createPending` → row in DB with the right fields.
- `markSent` → row updated + the nested SENT event created (the nested write).
- `recordOpen` → openCount incremented + OPENED event written.
- `findWithOpenEvents` / `findWithLink` → the relation include resolves.
- etc.

One test file per Prisma repo, covering every method on its interface.
